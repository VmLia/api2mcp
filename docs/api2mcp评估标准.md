## API2MCP 接口适配性评估规范

本规范用于评估一个 RESTful API 是否适合通过 api2mcp 转换为 MCP 工具。

---

### 五维评估模型

每个维度 0-20 分，总分 100。

| 维度 | 权重 | 评估要点 |
|------|------|----------|
| **参数语义化** | 20分 | 参数名是否自解释？是否有清晰的类型、枚举、单位描述？是否存在歧义"万能参数"？ |
| **参数确定性** | 20分 | 每个参数是否对应唯一的业务含义？参数间逻辑关系是否明确？是否存在一个参数同时影响多个字段？ |
| **响应可理解性** | 20分 | 返回结构是否扁平？字段是否有业务描述？是否暴露了无关调试信息？ |
| **文档完备性** | 20分 | 是否提供 OpenAPI/Swagger 文档？是否有请求/响应示例？是否有错误码说明？ |
| **安全与扩展性** | 20分 | 是否存在注入风险？参数是否可枚举校验？是否支持字段扩展而无需改接口？ |

**评级对照：**

| 总分 | 评级 | 处理建议 |
|------|------|----------|
| ≥ 80 | S 级（优秀） | 可直接自动注册为 MCP 工具 |
| 60-79 | A 级（需优化） | 可注册，但建议按改造建议调整 |
| < 60 | B 级（需改造） | 不建议直接注册，需先改造接口 |

---

### 各维度详细评分标准

#### 1. 参数语义化（20分）

| 分数 | 标准 |
|------|------|
| 18-20 | 参数名语义清晰（如 `keyword`、`category`、`price_min`），枚举值有中文描述，数值参数标注了单位 |
| 12-17 | 参数名基本可读，但缺少枚举说明或单位标注 |
| 6-11 | 存在万能参数（如 `query`、`filters`、`params`），参数含义需额外解释才能理解 |
| 0-5 | 参数全部使用缩写或无意义命名（如 `q`、`p1`、`p2`），无任何描述 |

#### 2. 参数确定性（20分）

| 分数 | 标准 |
|------|------|
| 18-20 | 每个参数独立对应一个业务字段，参数间关系为纯 AND 组合，行为完全可预测 |
| 12-17 | 大部分参数确定，但个别参数存在含义重叠或依赖关系未文档化 |
| 6-11 | 存在一个参数影响多个字段的情况，或参数间有隐式的 OR/互斥关系 |
| 0-5 | 参数行为完全由服务端动态决定，客户端无法预测调用结果 |

#### 3. 响应可理解性（20分）

| 分数 | 标准 |
|------|------|
| 18-20 | 返回结构扁平，字段名语义化，有 outputSchema 或字段说明，只返回业务数据 |
| 12-17 | 结构基本清晰，但少数字段名需要猜测含义 |
| 6-11 | 返回结构深层嵌套，或包含调试信息（如 `query_analysis`、`debug_info`、堆栈） |
| 0-5 | 直接返回原始数据库字段，无任何说明，或响应中混杂了错误堆栈 |

#### 4. 文档完备性（20分）

| 分数 | 标准 |
|------|------|
| 18-20 | 有标准 OpenAPI 3.x 文档，每个参数有 description/type/enum/example，有 responses 和错误码说明 |
| 12-17 | 有 OpenAPI 文档但部分参数缺少 description 或 example |
| 6-11 | 仅有代码注释，无正式 API 文档 |
| 0-5 | 无任何文档，接口只能靠猜测调用 |

#### 5. 安全与扩展性（20分）

| 分数 | 标准 |
|------|------|
| 18-20 | 使用字段白名单校验，参数值有枚举/范围限制，支持字段元数据发现接口 |
| 12-17 | 有基本校验但未使用白名单，或缺少字段元数据接口 |
| 6-11 | 存在 SQL 拼接风险，或参数无任何校验直接透传 |
| 0-5 | 直接拼接原始 SQL 无白名单无校验，存在注入风险（自动拒绝注册） |

## 打分举例

### 示例一：高分接口（92分 · S级）

**接口**：商品搜索 API  
**请求**：`GET /api/products/search?keyword=手机&category=electronics&price_min=1000&price_max=5000&brand=Apple&page=1&page_size=20`

**参数设计**：

| 参数 | 类型 | 说明 |
|------|------|------|
| keyword | string | 商品名称/描述关键词模糊搜索 |
| category | string(enum) | 商品分类：electronics（电子产品）、clothing（服装）、food（食品） |
| price_min | number | 最低价格（元） |
| price_max | number | 最高价格（元） |
| brand | string(enum) | 品牌名称：Apple、Samsung、Huawei、Xiaomi |
| page | integer | 页码（从1开始） |
| page_size | integer | 每页条数（最大100） |

**响应结构**：
```json
{
  "items": [
    {
      "id": "P001",
      "name": "iPhone 15",
      "category": "electronics",
      "price": 6999.00,
      "brand": "Apple",
      "stock": 120
    }
  ],
  "total": 45,
  "page": 1,
  "page_size": 20
}
```

**各维度打分**：

| 维度 | 得分 | 评语 |
|------|------|------|
| 参数语义化 | 19 | 参数名语义清晰，枚举值有中文说明，价格标注了单位 |
| 参数确定性 | 20 | 每个参数独立对应一个字段，纯 AND 组合，行为完全可预测 |
| 响应可理解性 | 18 | 扁平结构，返回纯业务数据，字段名自解释 |
| 文档完备性 | 18 | 有完整 OpenAPI 文档，含参数 example 和错误码 |
| 安全与扩展性 | 17 | 使用枚举校验 category/brand，有分页限制 |
| **总分** | **92** | **S级 · 可直接自动注册** |

---

### 示例二：低分接口（8分 · B级）

**接口**：订单查询 API  
**请求**：`GET /api/orders/query?q=2024年已完成订单&act=list`

**参数设计**：

| 参数 | 类型 | 说明 |
|------|------|------|
| q | string | 查询语句 |
| act | string | 操作类型 |

**响应结构**：
```json
{
  "code": 0,
  "msg": "ok",
  "d": {
    "l": [
      {
        "c1": "ORD001",
        "c2": 299.00,
        "c3": "completed",
        "c4": "2024-03-15",
        "c5": 9988776655
      }
    ],
    "t": 230,
    "debug": {
      "sql": "SELECT * FROM orders WHERE status='completed' AND year=2024",
      "cost_ms": 45,
      "hits": 230
    }
  }
}
```

**各维度打分**：

| 维度 | 得分 | 评语 |
|------|------|------|
| 参数语义化 | 2 | `q` 和 `act` 无法理解含义，万能参数 `q` 破坏了工具确定性 |
| 参数确定性 | 0 | 所有查询逻辑被塞进一个 `q` 参数，服务端自行解析，客户端完全无法预测行为 |
| 响应可理解性 | 2 | 字段使用无意义编码（`c1`-`c5`），暴露了 `debug` 信息（SQL 语句、执行耗时） |
| 文档完备性 | 4 | 无 OpenAPI 文档，无参数说明 |
| 安全与扩展性 | 0 | 直接在调试信息中暴露原始 SQL，存在严重注入风险 |
| **总分** | **8** | **B级 · 严重低于标准，必须彻底改造后才能注册** |

> **改造建议**：
> 1. 删除 `q` 万能参数，拆分为 `keyword`、`status`、`start_date`、`end_date` 等结构化参数
> 2. 响应字段改为语义化命名：`order_id`、`amount`、`status`、`create_date`
> 3. 删除 `debug` 字段，不在生产响应中暴露 SQL 和执行信息
> 4. 为所有参数添加 OpenAPI 文档说明
